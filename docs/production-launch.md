# 正式商店与自动到账确认

研究日期：2026-10-22。当前商户支付接口尚未开通；正式域名、服务器和商店名称待提供。此文档是接入方案，不代表支付接口已联调或正式站已部署。

## 已完成的正式版改动

- 非 GitHub 演示构建默认使用正式商店界面，不显示学习提示、DEMO 订单码、模拟支付成功按钮或示例账号密码。
- 店名通过 `NEXT_PUBLIC_STORE_NAME` 配置，未配置时显示“Muse 商店”；售后 QQ 3557785836。
- 保留成品账号 ¥15、100亿 Token ¥29、150亿 ¥45、200亿 ¥52、300亿 ¥79，无额外加价。
- 正式版创建订单请求服务器 `/api/orders`，只提交商品 ID、邀请码或邮箱、支付方式、条款确认及防重复请求 ID。金额由服务器按商品目录决定。
- 查询和付款状态更新使用 `/api/orders/lookup`，订单口令放在 POST 请求体，付款页面每五秒查询一次。服务器不可用时显示错误，不生成可付款订单。
- 账户资料只显示服务器提供的实际交付字段；没有资料时提示联系支持。

目前实现的是正式前端与接口协议，**后台订单接口、数据库、支付下单、验签回调、库存和邮件交付尚未实现或部署**。前端收到服务器的订单状态，才会展示付款和交付结果。后端未连接时，正式版会提示“在线支付尚未开通”。

## 自动确认到账如何实现

1. 服务端保存待支付订单：商品、实际金额（整数分）、支付方式、交付目标、过期时间、独立查询口令哈希。
2. 服务器调用商户支付接口，以本系统订单号下单，获得对应订单的付款链接，再通过本域二维码接口生成图片。不能把所有订单指向一张静态个人收款码。
3. 微信/支付宝将支付结果通知到公开 HTTPS 回调地址。后端验证签名，核对应用/商户、订单号、币种及金额，只接受可信的支付成功状态。
4. 支付通知可能重复或漏收。重复通知只记账一次，交易号设置唯一约束；漏收通过平台查单接口补查。查单也要使用服务端签名请求并验证响应。
5. 验证通过后，在数据库事务中将订单记为已付款，并创建待履约任务。浏览器“我已付款”、计时结束、截图、可编辑的本地状态都不能作为到账依据。
6. 到账确认和履约是两件事：账号需接库存及邮件，Token 充值需有实际充值接口或人工处理队列。不要在确认到账时直接宣称 Token 已到账。
7. 若付款晚于本地计时，仍按平台最终支付结果记账或进入人工处理，不能仅因页面超时忽略已收款。

## 支付通道与申请

### 微信

网站扫码支付通常采用商户 Native 支付。需要商户号、已授权/开通的产品能力、AppID、商户 API 证书与私钥、APIv3 密钥，以及微信支付公钥/平台证书配置。不同入驻主体和经营类目能开通的产品以平台审核结果为准。

- [Native 下单](https://pay.wechatpay.cn/doc/v3/merchant/4012525171)：服务端下单返回 `code_url`，用于为每个订单生成二维码。
- [支付成功回调与验签](https://pay.wechatpay.cn/doc/v3/merchant/4012791861)：验证请求头签名并处理通知；再解密资源并核对订单信息。
- [商户订单号查单](https://pay.wechatpay.cn/doc/v3/merchant/4012791900)：用于主动核实支付结果。
- [小微商户进件](https://pay.wechatpay.cn/doc/v3/partner/4012722249)：有相应权限的服务商可协助申请。是否支持本店经营内容和网站支付，仍需确认。

研究中还发现官方的[个人二维码收款开放](https://pay.wechatpay.cn/doc/v3/merchant/4012154495)。它用于小程序内的纯个人收付款，官方明确不支持商家收款，不能拿来替代本网站商户接入。

### 支付宝

用实名账号入驻开放平台、创建自用型应用，申请适合实际经营内容及网站场景的支付产品；是否批准以账号资质和产品审核为准。服务器配置应用 ID、应用私钥和支付宝验签公钥/证书，生成每笔交易，再接收并验证异步通知和查单结果。

- [开发者接入流程](https://openhome.alipay.com/platform/accessProcessPage.htm)
- [交易预创建 `alipay.trade.precreate`](https://developer.alibaba.com/docs/api.htm?apiId=862&docType=4)
- [交易查询说明](https://developer.alibaba.com/docs/doc.htm?articleId=757&docType=4&treeId=180)

如果采用服务商或聚合支付，只选能明确说明商户入驻、结算主体、签名算法、通知和查单接口的方案。拿到具体平台及文档后再写适配器，不能假定任意个人收款码都具备订单回调。

## 部署

GitHub 继续存放源码。正式电商站需要自己的域名、HTTPS、后端运行环境和持久数据库。[GitHub Pages 明确不用于电商交易托管](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)，现有 `github.io` 地址保持预览。不要把它的提示去掉就当作完成生产部署。

环境设置示例（仅前端）：

```text
NEXT_PUBLIC_PUBLIC_DEMO=false
NEXT_PUBLIC_STORE_NAME=你的商店名称
```

`NEXT_PUBLIC_BASE_PATH` 在正式根域名部署时留空，`GITHUB_PAGES` 不启用。执行 `npm run build` 与 `npm run start`。生产服务器必须提供下面的同域 API；当前仓库没有这些后台接口。支付私钥和数据库凭证必须保留在服务端环境，不能使用 `NEXT_PUBLIC_` 前缀。

## 待实现的订单 API 协议

创建：`POST /api/orders`

```json
{
  "requestId": "随机请求 ID，用于服务端幂等",
  "product": "muse-token",
  "planId": "100",
  "inviteCode": "买家账号邀请码",
  "method": "wechat",
  "acceptedTerms": true
}
```

账号商品的 `product` 为 `muse`，以 `email` 代替 `inviteCode`，无需 `planId`。后端应拒绝未知商品、非法档次、缺失联系字段、不支持的支付方式和未确认条款。不得接受前端提交的价格覆盖服务端目录。

查询：`POST /api/orders/lookup`，请求体为 `{"id":"订单号","token":"查询口令"}`。校验查询口令并限流，不能仅凭公开订单号返回邮箱、邀请码或交付密码。使用 HTTPS，响应禁止缓存。

返回订单示例：

```json
{
  "id": "服务器订单号，不使用 DEMO 前缀",
  "token": "服务器生成的高熵查询口令",
  "product": "muse-token",
  "title": "Muse Token · 100亿 Token",
  "inviteCode": "买家账号邀请码",
  "amountCents": 2900,
  "feeCents": 0,
  "method": "wechat",
  "expiresAt": 1790000000000,
  "status": "pending",
  "qrImageUrl": "/api/payments/qr/受保护的订单付款码地址"
}
```

状态约定：`pending` 待支付；`processing` 已核实到账、待履约；`complete` 已完成实际交付；`expired` 已关闭且未支付。账号交付完成时可附带 `delivery`，包含 `email`、`password`、`codeUrl`。后端应避免将敏感字段写进访问日志，并保护存储和备份。

上线前必须完成真实商户环境联调、回调验签/篡改金额/重复通知/漏回调查单测试、订单重启恢复、履约防重复、退款与对账流程。当前前端的测试接口响应只能验证界面，不能算作真实收款联调。
